# RP-001 ReleasePreparation and ReleaseVerification owner decisions

Wave: `RQW-BF39D9028F6F9289`

The owner approved all twenty-four recommendations in the exact breadth-first clarification wave.

1. **RP-Q-005**

   Should one ReleaseCandidate bind the exact source commit/tree, approved project baselines, package version, release configuration, toolchain identities, and EnvironmentReadinessReceipt?.

2. **RP-Q-003**

   Should ReleasePreparation be one conditional semantic module after SystemVerification, with a separate ReleaseVerificationGate deciding candidate readiness before BusinessAcceptance?.

3. **RP-Q-007**

   Should the required candidate set contain a deterministic installable tarball, release catalog/manifest, CycloneDX SBOM, SHA-256 ledger, release notes, license/notice material, and a compact evidence index?.

4. **RP-Q-001**

   Should RP-001 own preparation and verification of an exact release candidate only, while publication, deployment, protected-main promotion, and release approval remain outside its authority?.

5. **RP-Q-009**

   Should ReleaseVerification require static verification, the complete deterministic test suite, package/export enumeration, isolated install/import checks, SBOM and checksum verification, documentation/link checks, secret scanning, and a clean Windows Desktop consumer run?.

6. **RP-Q-013**

   Should evidence preserve exact commands, tool/adapter versions, configuration and input digests, exit codes, durations, stdout/stderr or artifact digests, candidate bytes, and checkpoint identities?.

7. **RP-Q-011**

   Should the successful Gate output be a ReleaseReadinessBaseline/record that authorizes only downstream human-controlled publication consideration and never performs publication or branch/tag mutation?.

8. **RP-Q-017**

   Should candidate materialization checkpoint exact prepared outputs before any merge or external effect, with exact replay performing zero packaging, download, signing, upload, tagging, or publication calls?.

9. **RP-Q-015**

   Should release execution be offline by default, allow only exact destination/purpose network grants, reject secret-bearing artifacts or logs, and require checksum-pinned project-local tools?.

10. **RP-Q-019**

   Should V1 ship deterministic native Node/Windows implementations for cataloging, packing, checksum/SBOM validation, and installed-package verification, with hosted release systems represented only by optional bounded adapters?.

11. **RP-Q-023**

   Should deterministic byte equality, fail-closed validation, zero-call replay, crash recovery, redaction, isolated clean-install verification, and honest adapter maturity be mandatory release acceptance properties?.

12. **RP-Q-021**

   Should Desktop present one compact candidate/readiness summary containing blockers, warnings, version/source identity, artifact digests, verification coverage, and direct evidence links?.

13. **RP-Q-006**

   Should any source, configuration, version, tool, baseline, or environment drift create a new immutable candidate attempt instead of updating historical candidate evidence?.

14. **RP-Q-004**

   Should RP-001 require an accepted current EnvironmentReadinessReceipt before candidate materialization and revalidate it before every effectful release step?.

15. **RP-Q-008**

   Should source archives generated by GitHub remain externally produced publication artifacts, while RP-001 verifies their expected source identity but never predicts or self-certifies their final bytes?.

16. **RP-Q-002**

   Should RP-001 cover GitHub source plus an installable library tarball for ChatGPT/Codex Desktop on Windows, while public npm, one-click Desktop installation, hosted operation, and non-Windows claims remain excluded?.

17. **RP-Q-010**

   Should every verification family be required unless ReleaseVerificationGate records an explicit policy-backed ApprovedNotApplicable disposition, with failed, missing, stale, or unknown required evidence blocking readiness?.

18. **RP-Q-014**

   Should trusted contributors project only forward factual links from approved source and environment state through candidate artifacts and verification evidence, while adapters receive no graph access?.

19. **RP-Q-012**

   Should version selection, changelog approval, prerelease versus stable designation, and final publication approval remain explicit owner decisions rather than adapter- or Core-inferred values?.

20. **RP-Q-018**

   Should verification re-load candidate bytes from content-addressed storage and reject rebuilt, substituted, partially retrieved, or digest-mismatched artifacts?.

21. **RP-Q-016**

   Should RP-001 fail closed on dependency, action-pin, license, provenance, SBOM, checksum, signature/attestation, or secret-scan findings according to one versioned release policy?.

22. **RP-Q-020**

   Should adapter slots be capability-oriented—materialize, inspect, verify, attest, and publication-prerequisite probe—with no product-specific routing in Generic Core and no silent fallback?.

23. **RP-Q-024**

   Should V1 record materialization and verification duration, cache hits, retries, artifact sizes, and bottlenecks without imposing a universal wall-clock SLA until Windows reference-host measurements establish one?.

24. **RP-Q-022**

   Should all proposed network, signing, credential, filesystem, process, tag, or remote-repository effects be consolidated and shown for explicit approval before execution?.
